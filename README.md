# Pro Transfer V7

Secure one-to-one file/folder transfer utility written in Go.

V7 keeps the V6 transport engine and replaces the long invitation string with a **four-word PAKE code**:

```text
silvercastle-mangostream-orbitrocket-velvettiger
```

The user shares only those four words. The relay never receives the phrase itself.

## Highlights

- 1 sender + 1 receiver per transfer
- one file, many files, folders, or mixed inputs
- nested and empty folders, zero-byte files
- no manual ZIP/unzip
- four-word human-readable invitation code
- identity/session-bound P-256 PAKE with mutual key confirmation
- fresh random 256-bit transfer secret delivered only after PAKE succeeds
- AES-256-GCM end-to-end encrypted manifest and payload chunks
- fresh random GCM nonce for every transmitted/retransmitted chunk
- SHA-256 final verification for every file
- automatic same-LAN direct fast path
- encrypted/authenticated LAN route negotiation after PAKE
- automatic public-relay fallback
- 1..8 parallel public TCP data streams (default 4)
- authenticated per-stream resume after disconnects
- secret-derived reconnect aliases and data-channel credentials
- no file storage on the live relay
- path-traversal protection; symlinks rejected
- progress, speed and ETA
- automatic Windows User PATH registration
- automatic `config.json` creation
- Railway-ready Dockerfile

## Four-word security design

Each printed token comes from a 4096-entry generated human-readable dictionary. Four tokens provide about 48 bits of invitation entropy.

V7 deliberately does **not** hash the complete phrase into a public room, because that would provide an offline verifier for the human code. Instead, only a small routing slice is used to derive an opaque rendezvous room. The remaining uncertainty stays behind PAKE; the default server also limits initial PAKE attempts per room.

The four words are **not** used as the AES key. The flow is:

```text
4-word phrase
     |
     +--> opaque rendezvous selector --> relay
     |
     +--> PAKE sender <-------------> PAKE receiver
                    |
             mutual confirmation
                    |
             PAKE channel key
                    |
       decrypt random 256-bit transfer secret
                    |
             HKDF-SHA256
          /         |          \
 manifest key   payload key   LAN/resume credentials
```

The random transfer secret is generated by the sender before the transfer. It is wrapped with AES-GCM under the PAKE-derived channel key and forwarded through the relay as ciphertext. LAN candidates are inside the same authenticated encrypted envelope.

The relay can see operational metadata needed for routing (opaque room, aggregate sizes, stream identifiers/timing), but it does not receive the four-word phrase, plaintext file/folder names, plaintext manifest, file contents, or the random E2E transfer secret.

`internal/transfer/pake_p256.go` contains a narrowly scoped adaptation of the P-256 path from `github.com/schollz/pake/v3`; see `THIRD_PARTY_NOTICES.md`. This implementation is tested for key agreement, wrong-passphrase rejection and mutual confirmation.

## Usage

Send one file:

```powershell
transfer send report.xlsx
```

Send many files:

```powershell
transfer send report.xlsx photo.jpg data.csv
```

Send a folder:

```powershell
transfer send "D:\Projects\My Project"
```

Mixed:

```powershell
transfer send report.xlsx "D:\Projects\My Project" photo.jpg
```

Sender prints:

```text
==============================================================
 TRANSFER CODE:
 silvercastle-mangostream-orbitrocket-velvettiger
==============================================================
```

Receiver:

```powershell
transfer receive silvercastle-mangostream-orbitrocket-velvettiger
```

Codes are case-insensitive. A quoted space-separated form is also accepted.

## Automatic LAN direct

When `network.lan_direct=true`, the sender opens a temporary authenticated local endpoint. LAN addresses are **not put in the visible code**. They are delivered to the receiver only after PAKE succeeds.

```text
Sender ---- public relay ---- Receiver
   |            |                |
   |      PAKE rendezvous        |
   |            |                |
   |<------ encrypted LAN negotiation ------>|
   |                             |
   +========== direct LAN =======+

public relay room is cancelled after LAN wins
```

The receiver accepts only suitable local/private route candidates and authenticates the direct endpoint with a credential derived from the random transfer secret. If direct LAN cannot be reached, it automatically stays on the public relay.

LAN direct is not Internet NAT traversal; it is intended for peers that can directly reach each other on the same LAN/Wi-Fi/VPN.

## Public relay and parallel streams

When LAN direct is unavailable, V7 can use multiple TCP payload streams:

```text
control
  +-- data stream 0
  +-- data stream 1
  +-- data stream 2
  +-- data stream 3
```

Each stream has independent authenticated resume state. If one stream fails, successfully completed ranges on other streams are kept and only missing ranges continue after reconnect.

Parallel streams can improve WAN throughput when a single TCP flow is constrained by routing/latency, but cannot exceed the actual sender upload, receiver download, relay or ISP bandwidth.

## Resume

Receiver staging state is kept under the configured download directory:

```text
downloads/
└── .protransfer-<room>-<transfer-id>/
    ├── state.json
    └── content/
```

Only complete AES-GCM-authenticated chunks advance resume state. After every file passes SHA-256 verification, final roots are moved into the download directory and temporary state is removed.

## Default client config

```json
{
  "server": "localhost:8080",
  "download_dir": "downloads",
  "tls": {
    "enabled": false,
    "insecure_skip_verify": false
  },
  "timeouts": {
    "connect": "10s",
    "io": "2h"
  },
  "network": {
    "lan_direct": true,
    "parallel_streams": 4
  }
}
```

`parallel_streams` accepts `1..8`.

For Railway, set `server` to the **public TCP Proxy** host and port, not `*.railway.internal`.

## Server

```bash
./server -addr :8080
```

Important options:

```text
-addr :8080
-max-transfer-gb 10
-room-ttl 10m
-transfer-timeout 2h
-resume-grace 2m
-max-rooms 100
-max-manifest-mb 2
-max-connections 240
-max-handshakes-per-minute 600
-max-pake-attempts 16
```

The PAKE-attempt limit is per room and reduces online guessing of the human invitation phrase. The global TCP handshake limit is per source IP/minute and also protects connection resources.

Optional transport TLS:

```bash
./server -addr :8443 -tls-cert fullchain.pem -tls-key privkey.pem
```

End-to-end payload encryption remains active regardless of transport TLS.

## Railway

The root `Dockerfile` builds and starts `./cmd/server` automatically.

Configure:

```text
TCP Proxy target port: 8080
Replicas: 1
```

Use one replica because room/session state is currently in process memory.

With four parallel streams one fully active public-relay transfer can temporarily consume roughly ten TCP connections (two control + four sender data + four receiver data). LAN direct payloads do not consume relay data-stream connections.
